# src/server/routes

Fastify route plugins, registered by `buildApp` in `../app.ts` under the `/api` prefix. Every route here is default-deny unless it sets `config: { public: true }`.

| Path | What it is | Read it when |
| --- | --- | --- |
| `health.ts` | `GET /api/health` returns `{ "status": "ok" }`. Public | Health checks, or an example of a public route |
| `auth.ts` | `authRoutes`: public `GET /api/auth/config` (`{ mode, registration }`), `GET /api/auth/me` (`{ email, authMethod }`, session required), and public `POST /api/auth/register` (always 202 `{status:"verification_sent"}` with no cookie, 400 `invalid_request`, 403 `registration_disabled` (not for an `ADMIN_EMAILS` email while the ceiling is on) / `local_auth_disabled`), public `POST /api/auth/verify-email` (body `token` and `password`; checks the password against the token's pending Argon2id hash; 204 no cookie, 400 `invalid_request` / `invalid_token` / `token_without_password`, 401 `invalid_password` (every attempt counts per token and per owner email, 5 per 15 min, in a limiter of its own (its email, token and IP keys are all separate from login and register), before any Argon2 work; each attempt is charged (`failed_attempts` on the row, via `recordFailedEmailVerification`) right after the limiter takes and before Argon2, so the token is burned by the fifth attempt in total, whatever the time window, and a correct password on the fifth attempt gets 401 `invalid_password`; after the burn even the correct password gets 400 `invalid_token`; when the token key refuses, the token is deleted and Argon2 is skipped; when the owner's verify-email email key refuses it gives 429 `rate_limited` with `Retry-After`, keeps the token, does not count a wrong password and skips Argon2; a correct password whose consume fails also gives 401), a verified owner's token gives the same 400 `invalid_token` as an unknown one, success deletes all the user's tokens, 403 `local_auth_disabled`; its own per-IP limit of 20 per 15 min against guessing across many tokens, not shared with login and register, 429 `rate_limited`), and an unverified user's login gets the same 401 and `POST /api/auth/login` (200, 400 `invalid_request`, 401 `invalid_credentials`, 403 `local_auth_disabled`). Both return 429 `rate_limited` with `Retry-After` once an email (5 per 15 min, shared by both) or a client IP (20 per 15 min) is over its limit (verify-email has separate counters). Needs `secureCookies`, `now`, `mailer` and `publicOrigin` options from `app.ts`. Uses `auth/passwords.ts`, `auth/sessions.ts`, `db/accounts.ts`, `db/lookup.ts` | Changing what the browser learns about auth or the signed-in user |

| `integrations.ts` | `integrationRoutes` with `{ deps: CreateDeps }`: `POST /api/integrations/actual-schedules` (body `wallosSubscriptionId`, `accountId`, `payee`, `categoryId?`; 201 ids and flags) and `POST /api/integrations/wallos-subscriptions` (body `scheduleId`; 201 `wallosSubscriptionId`). #108: after a successful create both save the pair as a LINKED match through `../matching/link-created.ts` and add `matchId` and `matchCreated` (false when a match already covered one of the items) to the 201. | `matches.ts` | `matchesRoutes` with `{ deps: Pick<CreateDeps, 'wallos' | 'repoFor' | 'withActual'> }`: `POST /api/matches/:id/resolve` (body `action`, `confirm?`). Built: `ignore_diff` (MISMATCH_DETECTED only, re-reads both sides read-only via `readCurrentSides` in `../matching/sync-check.ts`, then in one update sets LINKED and stores the server-computed current hashes; 400 `invalid_state` and no write if a side is missing or unhashable; client hashes are never used) and `unlink` (needs `confirm: true`, LINKED or MISMATCH_DETECTED, deletes the row). `overwrite_wallos` / `overwrite_actual` need `confirm: true` and MISMATCH_DETECTED, snapshot the target, write, re-read and store server hashes (see `matching/overwrite.ts`); extra codes 400 `range_amount_unsupported` / `patterns_unsupported`, 502 `overwrite_unverified`. Other actions give 400 `unsupported_action`. Also 400 `invalid_request` / `confirmation_required` / `invalid_state`, 404 `match_not_found`. Only the two overwrite actions write to Wallos or Actual. Also #109 `POST /api/matches/:id/relink` (body `itemId`; LINKED or MISMATCH_DETECTED row with one side gone; the missing side is derived from `readCurrentSides`, never from the client; 404 `match_not_found`, 400 `invalid_state` / `item_not_found` / `invalid_request`, 409 `already_matched` (item has a row on either side, checked before any remote read, or a unique violation); no candidate rule, an unhashable item stores a null hash; `repo.replaceMatchSide` with server hashes; 200 `{id,status:'LINKED'}` with the same id; reads only, never writes to Wallos or Actual). Registered in `app.ts` next to `syncRoutes` | Changing the match routes |
