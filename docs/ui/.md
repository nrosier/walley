# UI/UX Migration Plan

> **Template material: most phases do not apply to Walley. See WALLEY-UI-SPEC.md for Walley's plan.** Sections and phases marked "N/A for Walley" describe record, route, and sync-engine work that Walley does not have. The remaining phases are kept as generic guidance.

**Status:** Implementation plan for the target experience  
**Audience:** Coding agents and human contributors  
**Related documents:** [Normative UI/UX guide](UI-UX_GUIDELINES.md)

This document explains how to move the current interface to the target UI/UX without changing domain calculations, stored data guarantees, persistence, or export accuracy. The guide defines how the finished product must behave. This plan defines implementation order, integration points, migration boundaries, and acceptance criteria.

The target is a coherent redesign. Existing UI patterns are implementation evidence, not patterns that must be preserved. Keep existing behavior only when it remains correct under the normative guide.

## 1. Outcomes that are not negotiable (N/A for Walley)

The migration is complete only when all of these statements are true:

1. A record is the persistent context for record-specific work, and switching records does not require returning to the record list.
2. Navigation is grouped by user goal. It has no third menu level and no generic collection of unrelated feature links.
3. Each feature has one application destination, one choice control for each of its variants, and one local view navigation.
4. Result views keep their selection feedback next to the visualization that produced it. Exports keep a complete printable artifact.
5. Selecting an item in a visualization updates one nearby selection inspector. It appears beside the visualization when both remain usable and immediately below otherwise.
6. Durable account and device preferences live in a stable Preferences workspace. Page and result settings use inline controls or one staged modal according to their size.
7. Record facts, account preferences, device preferences, saved-configuration overrides, page state, and request consent remain separate scopes.
8. Text, date, number, select, checkbox, radio, switch, disclosure, dialog, status, empty-state, and table behavior comes from the shared component layer.
9. Related settings for one result apply together through one staged dialog. No nested or duplicate settings surface remains.
10. Obsolete route shapes, duplicated navigation, and superseded controls are removed rather than maintained as compatibility paths.
11. Every existing stored record remains readable and editable from both the local store and the synchronized server store.
12. Every changed surface works in every supported language, light and dark themes, keyboard-only use, and the required viewport matrix.

## 2. Target information architecture (N/A for Walley)

Use a responsive workspace shell. On wide layouts, render a collapsible rail and a focused content area. On narrow layouts, render the same navigation as a drawer. Do not maintain separate desktop and mobile navigation definitions.

```text
<App name>
├ <Records area>
│ └ Current record: <name> [switch]
│   ├ Overview
│   ├ Edit details
│   └ <Feature groups>
├ <Tools / Explore>
│ └ <Tool groups>
├ Documents
├ Preferences
└ Account / Admin when applicable
```

Group labels are grouping labels. On a desktop rail, their children may remain visible. In a narrow drawer they may expand once. Do not add another flyout or another row of submenus after navigation.

The content header always contains:

1. A title naming the feature and subject, such as **Matches · Netflix**.
2. A concise context line containing the effective basis or other scope.
3. Actions that affect this page, including its export actions.
4. Advanced settings only when they affect this page or result.

## 3. Canonical routes and clean cutover (N/A for Walley)

Keep hash routing so the built application can run as static files. New links should express the target hierarchy, with one canonical hash per destination. Use placeholder segments such as `:recordId` and `:section` in the route table, and list each concrete destination in the route module.

Routes that cannot be reached from the navigation are removed, not redirected. A settings section route (`#/<settings>/:section`) deep-links to one settings group.

Replace the current route scheme in one coordinated cutover. The route module should parse and construct only the canonical routes after the shell migration lands. Remove obsolete path expressions, query parameters, route constructors, and compatibility branches. An obsolete or malformed hash may use the existing safe fallback to the home view; do not redirect it to a guessed destination or keep aliases for it.

Because the hash identifies the application route, encode an optional in-view focus as a query parameter rather than a second hash. Scroll only after the destination heading exists, respect reduced motion, and move focus only when the user explicitly navigated to the subsection.

Add canonical route tests before changing navigation. Cover every target destination, route construction and parsing round trips, query handling, and invalid record IDs. Update or replace tests for obsolete routes in the same slice; obsolete paths should no longer be constructed or treated as supported behavior.

## 4. Stored record compatibility (N/A for Walley)

UI and route compatibility may change. Stored record data is the compatibility boundary and must survive unchanged.

Records must continue to be read and written through the existing store and domain helpers. Do not replace the store with component state, serialize a new record object directly, rename stored fields, regenerate record IDs, or clear the database during route migration. Any schema or version change that the migration needs must be a separate, reviewed change with its own migration.

Preserve these storage contracts:

1. The database layer remains the durable store. A UI-only migration does not require a schema-version bump.
2. The operation or write path remains unchanged. Do not change the stored format for UI work.
3. The fold or materialization step remains the only path from stored operations to materialized records. Unknown, incomplete, deleted, restored, and purged records retain their current behavior.
4. The sync engine continues to push and pull the same records. The server relay remains an encrypted, user-scoped relay and does not need a schema or route migration for UI work.
5. Record forms continue to use the existing draft, validation, and mutation helpers. Changing field components must not change stored values.

Before the first redesigned record or shell screen lands, add a durable compatibility fixture containing one complete record and one incomplete record. Verify all of the following:

- Opening an existing database preserves every operation, snapshot recovery, device ID, record ID, deletion state, and field value.
- Materialization returns the same record values before and after the UI migration.
- The redesigned list, overview, and edit screens can read the fixture without rewriting it.
- Saving one edited field appends only the expected change and leaves every untouched field unchanged.
- Pulling the same fixture through the server sync path produces the same materialized records as the local fixture.
- Sign-out, sign-in, account adoption, route changes, and application reload preserve records according to the existing per-account separation. Only the existing explicit remove-local-data or permanent-purge actions may delete them.

Keep the existing data-loss tests and the synchronization tests. Add one UI-level compatibility test that seeds existing stored records rather than creating the record through the redesigned form; otherwise the test would prove only that the new writer can read its own output.

## 5. New component and metadata boundaries

### 5.1 Feature registry (N/A for Walley)

Create a feature registry module as a pure TypeScript source of user-facing feature metadata. A definition should include at least:

```ts
interface FeatureDefinition {
  readonly key: FeatureKey;
  readonly scope: 'record' | 'global' | 'document' | 'preferences' | 'admin';
  readonly group: FeatureGroup;
  readonly order: number;
  readonly routeKind: Route['kind'];
  readonly buildHref: (context: FeatureContext) => string;
  readonly requiresRecordPrerequisite: boolean;
  readonly settingsMode: 'none' | 'inline' | 'staged-dialog' | 'workspace';
  readonly exportCapabilities: readonly ExportCapability[];
  readonly labelKey: FeatureLabelKey;
}
```

Derive record navigation, tool navigation, active state, prerequisite handling, and page-export registration from this registry. During transition, existing navigation modules may adapt or re-export registry results so existing callers continue to compile. Delete duplicated arrays when the last caller moves.

Add an exhaustiveness test that fails when:

- A user-facing `Route` has no feature metadata.
- Two features claim the same key, the same order in one group, or the same canonical href.
- A feature refers to a missing label in any supported language.
- A page export is registered for a feature that does not declare it.

### 5.2 Settings registry (N/A for Walley)

Create a settings registry as pure metadata. Do not make it a second storage system. Existing stores remain responsible for values until each setting is deliberately migrated.

Each setting definition declares:

- Stable key and value version.
- Owner and scope: application, account, device, record, saved item, page, or request.
- Default and reset target.
- Persistence and synchronization behavior.
- Editing surface and commit mode.
- Whether it is sensitive or included in share/export data.
- Parser, validator, and migration for persisted values.

Tests must reject combinations such as request consent with persistence, device presentation settings with account synchronization, or an immediately persisted setting inside a staged page dialog.

### 5.3 Shared UI primitives

Create the shared primitives in `<ui-primitives-dir>` with its own `MAP.md`. Keep business logic outside these components. Begin with:

- `Button`
- `Field`, `TextField`, `DateField`, `NumberField`
- `Select`, `Combobox`
- `Checkbox`, `Radio`, `Switch`, `ChoiceGroup`, `OptionCards`
- `Dialog`, `Disclosure`
- `FilterSummary`
- `SelectionInspector`
- `StatusMessage`, `EmptyState`
- `DataTable`

All interactive elements (buttons, inputs, selects, badges, textareas, toggles) come from `<ui-primitives-dir>`, and `<primitive-enforcement-test>` checks that no screen writes them directly.

Use real HTML inputs, buttons, links, fieldsets, tables, and dialogs. The primitive owns anatomy, states, keyboard behavior, and accessible relationships. The feature owns labels, options, validation rules, values, and domain consequences.

Do not create wrappers that merely rename raw elements. A primitive is ready when equivalent controls no longer need feature-specific state CSS or behavior.

## 6. Migration sequence

Implement the work in the following order. Each phase must leave the application releasable; do not open one branch containing the entire redesign.

### Phase 0: Freeze behavior and record baselines (N/A for Walley)

**Goal:** Protect calculations and important workflows before structural UI changes.

1. Record the current route, input, output, selection, export, and storage behavior used by existing end-to-end tests.
2. Add tests for the canonical route contract before switching navigation. Existing route tests may be replaced in the same slice because the current hashes have no production compatibility requirement.
3. Add screenshots only for surfaces whose visual structure is about to change. Cover both themes at 390×844, 1280×800, and 1440×900. Use assertions for behavior and accessibility; do not use screenshots as the only test.
4. Record current eager bundle size and the lazy-loaded feature chunks.
5. Add the stored-record compatibility fixture and prove it materializes identically from local and synchronized records.
6. Confirm all unrelated working-tree changes remain outside the UI migration.

**Complete when:** `<check-command>`, the relevant end-to-end tests, and the bundle-size check pass before the first UI change.

### Phase 1: Tokens and shared controls

**Goal:** Stop visual and behavioral drift before moving screens.

Primary integration point: `<ui-tokens-file>`.

1. Introduce the semantic color, type, spacing, control, radius, elevation, and motion tokens defined in the audit.
2. Bind `color-scheme` to the effective application theme.
3. Implement `Field`, `TextField`, `DateField`, `NumberField`, `Select`, Checkbox, Radio, ChoiceGroup, OptionCards, and Button first.
4. Suppress browser-dependent number spinners only after the shared accessible stepper exists.
5. Implement the standard and compact sizes. Compact controls return to standard touch targets on coarse-pointer layouts.
6. Migrate one representative form, one filter, and one settings dialog before broad rollout. Choose pilots from the existing forms, filters, and dialogs that use the most controls.
7. Remove the layout container class as the source of control appearance. It may remain a layout class.

**Acceptance criteria:**

- Equivalent controls have identical label, help, error, focus, hover, disabled, busy, and sizing behavior.
- Date fields remain typeable and store ISO values independently of localized display.
- Number steppers expose named Increase/Decrease buttons and Arrow Up/Down behavior.
- Every supported language's labels fit without truncating controls.
- Both themes meet WCAG AA for every state.

### Phase 2: Registries, canonical routes, and shell (N/A for Walley)

**Goal:** Establish one information architecture before restyling individual feature pages.

Primary integration points: the route module, the application root component, the navigation components, the feature registry, and the export registry.

1. Add the feature registry and canonical route constructors.
2. Replace current parsing and route construction with the canonical routes; remove old path and query forms in the same slice.
3. Create the workspace shell, navigation, record switcher, and page-header components. Keep the skip link and one `<main>` landmark.
4. Create a record overview screen. Complete records land there; incomplete or new records land on the edit form until prerequisites are met.
5. Replace the static current-record label with a searchable switcher. Preserve the current feature when the selected record meets its prerequisites; otherwise explain the requirement and route to the recovery action.
6. Move current-page exports into the page header. Move document builders to Documents. Move full-data exports to Preferences → Data & privacy.
7. Replace generic tool menus with the registry-driven groups. Global routes show **Return to {record}** only as history and **Using {record}** only when the tool consumes that record.
8. Collapse the desktop rail without losing labels to tooltips alone. On narrow screens use one drawer with the same data and grouping.

**Acceptance criteria:**

- Users can identify the current record, feature, and basis within three seconds.
- Switching records takes at most two actions.
- Every primary feature is reachable through no more than one expandable group.
- Navigation active state, titles, breadcrumbs, and exports all come from the same feature metadata.
- Back, forward, reload, and newly generated shared links retain meaningful behavior.
- Escape, outside interaction, route change, and focus departure close temporary navigation and restore focus correctly.

### Phase 3: Preferences and defaults (N/A for Walley)

**Goal:** Make scope, persistence, and defaults predictable.

1. Add settings route variants to the route module and lazy-load the Preferences view with its own message catalogue.
2. Render the Preferences groups as stable subsections. Use ordinary links on wide layouts and the shared Select on narrow layouts if the subsection navigation cannot fit.
3. Migrate language, regional formatting, default filters, matching tolerance, base currency, theme, symbols, density, and motion to the settings registry.
4. Keep account values local-first. Synchronize them only when the account model supports it; never make offline use depend on sign-in.
5. Keep device presentation settings on the device. Do not upload them as account preferences.
6. Show save and sync state inline. Do not add a page-wide Apply, Done, or Cancel action.
7. Keep optional frequent shortcuts, such as theme, synchronized with the canonical setting rather than creating another source of truth.
8. Every page that shows a result displays its effective basis and the source of any override.

**Defaults and override precedence:**

```text
Application default
  → user's default
    → saved configuration override
      → temporary page override
```

Device presentation settings apply independently. Record data never enters this precedence chain.

**Acceptance criteria:**

- Changes inside a staged dialog never bypass Cancel.
- **Apply to this result** never changes the user's default.
- **Save as my default** is a separate intentional action.
- Choosing any preset replaces every preset-owned draft value; it never inherits stale values from the previous selection.
- Changing any preset-owned value displays **Custom**, and returning every value to a preset restores that preset's name.
- Saved, shared, and exported results preserve the concrete effective values.
- Reset names its target.
- Request-specific AI consent remains unchecked and unpersisted.

### Phase 4: Result views and selection (N/A for Walley)

**Goal:** Preserve the strongest interaction in the existing result views while removing page-length friction.

Create these boundaries or equivalent boundaries with the same responsibilities:

- A workspace component that loads or receives one computed result and owns result-level settings.
- A header component: title, variant choice, basis, settings, and exports.
- A view navigation component: ordinary route links on wide layouts and one Select on narrow layouts.
- Focused view components, one per result view.
- `SelectionInspector`: common selected-item facts, meaning, related connections, Clear, and optional deeper disclosure.

Implement in this order:

1. Add the target result views and move each old section's content to its target view. Remove the old section parameter contract when the new navigation lands.
2. Replace any variant pills with one labelled Select in the header. Remove variants from application navigation.
3. Extract the existing visualization renderer from any combined on-screen layout without changing geometry or hit targets.
4. Render the visualization followed by `SelectionInspector` in DOM order inside one container.
5. Make the container an inline-size query container. Below the wide-layout threshold, use one column with the inspector immediately after the visualization. At and above it, use two columns. The visualization remains first in DOM and focus order, and the inspector does not get an independent vertical scrollbar.
6. Keep the combined renderer for exports, where a complete printable artifact is useful. Screen and export composition may differ while using the same computed data.

Use one selection model with a discriminated union for each selectable item type. Selection changes must update:

- Visual emphasis.
- The inspector heading and facts.
- Deterministic interpretation text.
- Related connections.
- The equivalent accessible table row and its selected state.
- Clear-selection behavior.

Do not let optional AI output replace deterministic facts or stored text.

**Acceptance criteria:**

- The application navigation contains one destination for each result type.
- Each variant appears once.
- Only one view navigation is visible.
- A selected item's meaning remains in the first adjacent region on every viewport.
- The inspector reserves enough space to avoid a large first-selection jump.
- Keyboard users can create and clear the equivalent selection through the accessible table.
- The combined SVG, PNG, print, and PDF exports remain equivalent to their pre-migration outputs.

### Phase 5: Staged settings for dense results

**Goal:** Turn a wall of related controls into one understandable task.

1. Create a staged settings dialog using the shared dialog primitive.
2. Move the related groups into its draft state, with one visible group per concern.
3. Show an applied-state summary beside the trigger, for example **4 types · 10 items · Option off**.
4. Apply and validate the complete draft once. Trigger one recalculation after commit.
5. Cancel, Escape, close, and backdrop discard the draft and restore focus.
6. Keep the last valid result visible with an updating state while recalculating.
7. Replace each bare native disclosure row with the shared Disclosure component, including its name, a glyph if one helps, the count of selected items, explicit Show/Hide wording, and a chevron.
8. Preserve export actions in the page header.

**Acceptance criteria:**

- Opening and cancelling settings never changes the result.
- Applying several changes causes one committed recalculation.
- No nested settings surface or duplicate control remains.
- The dialog remains operable at 390×844 and short laptop heights.
- Expandable content is visibly expandable without relying on a triangle, glyph, or color.

### Phase 6: Migrate remaining screens

**Goal:** Apply the shared grammar everywhere and remove one-off patterns.

Migrate by interaction family rather than by arbitrary file order:

| Family                  | First targets                                            | Required result                                                                                         |
| ----------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Dates and numbers       | Entry forms, date-range filters, document builder        | Shared editable DateField and NumberField; deterministic formatting                                     |
| Method choices          | Each short set of exclusive options                      | Segmented control or explanatory option cards according to the decision matrix                          |
| Filters                 | Lists and periodic views                                 | Visible presets, shown/total summary, one Change filters action, staged advanced dialog                 |
| Long forms              | Entry forms and document builder                         | Completion/dirty state, reachable primary action, grouped disclosures, sticky summary where appropriate |
| Dense tables            | Data tables, admin                                       | Typed alignment, sticky headers, compact desktop density, contained horizontal overflow                 |
| Expandable explanations | Any native disclosure element                            | Shared Disclosure                                                                                       |
| Result state            | Every screen that calculates or loads data               | Initial, updating, empty, zero, partial, error, offline, and success states                             |

Delete feature-specific CSS only after the feature uses the shared primitive and its tests cover the new states.

### Phase 7: Cleanup and enforcement

**Goal:** Make regression toward the old UI difficult.

1. Remove obsolete tabs, variant pills, duplicated navigation lists, raw settings controls, and unused CSS.
2. Add lint or test enforcement for the feature and settings registries.
3. Add a test that flags raw user-facing `input`, `select`, and dialog styling outside the primitive layer, allowing documented exceptions for hidden native inputs and specialized visualization controls.
4. Update the `MAP.md` files, test maps, route comments, language catalogues, and end-to-end support helpers.
5. Re-check bundle splitting. Do not eagerly load heavy feature, Preferences, document, or admin screens merely because the shell references their metadata.
6. Run the complete verification matrix and perform manual keyboard and screen-reader checks.

## 7. State and interaction contracts

### Immediate preferences

Account and device preferences update the local source of truth immediately. Show **Saving…**, **Saved**, or a recoverable synchronization error. A valid offline change remains applied when remote synchronization fails.

### Staged page or result settings

Opening copies applied values into a draft. Apply validates and commits the entire draft. Cancel, Escape, close, and backdrop discard it. Reset changes the draft only. No child control writes directly to global storage.

### URL state

Encode state when Back, reload, bookmarking, or sharing should reproduce it. This includes the current view, meaningful result dates, comparison target when safe, and applied settings when sharing the result is a product requirement. Do not place personal data, free text, consent, tokens, or other sensitive values in the URL.

### Loading and recalculation

On first load, reserve result geometry with a content-shaped placeholder. During recalculation, retain the last valid result, mark it as updating, and set `aria-busy` on the result region. Replace it only when the complete new result is available.

### Destructive actions

Prefer restore or Undo for ordinary deletion. Permanent deletion names the affected item or data set, explains local and synchronized consequences, and uses a dedicated destructive confirmation.

## 8. Responsive layout contracts

Verify 390×844, 768×1024, 1280×800, 1440×900, and 3440×1440.

- The workspace rail collapses when it would take useful width from the content.
- Result columns respond to their container, not a global viewport guess.
- Two-column result layouts appear only when both columns stay usable, and stack otherwise.
- The inspector moves below before either column becomes cramped and never receives independent vertical scrolling.
- Reading content stays near 68 characters per line.
- Tables and large visualizations use a wider data shell.
- Full-screen mobile dialogs retain visible title and action regions without trapping content beneath browser chrome.
- Sticky regions never consume most of a short viewport.
- Ultra-wide layouts expand data views rather than stretching prose.

## 9. Test changes required by the migration

Update tests as behavior moves. Do not delete assertions merely because old selectors no longer exist.

### Unit and component tests

Add or extend:

- Route tests: canonical route round trips, invalid IDs, query handling, and result views.
- Feature registry tests: coverage, ordering, prerequisites, exports, and label parity.
- Settings registry tests: valid scope, persistence, and commit combinations, and migrations.
- Existing store, fold, and sync suites plus a UI-level seeded fixture: existing local and synchronized data remain byte-for-byte interpretable.
- Primitive tests for labels, help and errors, number stepping, choice semantics, disclosure, dialog commit and cancel, and selection state.
- Existing selection tests: one selection model drives the visualization, inspector, and table.
- Existing formatter tests: deterministic dates, times, numbers, currency, and units.

### End-to-end tests

Refactor existing tests around roles, names, routes, and user-visible outcomes: navigation and item selection, focus restoration, result views and exports, staged settings draft semantics, Preferences location, no immediate mutation from staged dialogs, and accessibility (landmarks, axe, keyboard flow, focus order, responsive overflow, and table equivalents).

Add explicit checks at 390×844 and 1280×800 for every changed workflow. Add 3440×1440 coverage for wide result views and dense tables.

Manual checks remain required for:

- A screen reader such as VoiceOver or NVDA.
- Browser zoom at 200% and text zoom where supported.
- High-contrast and forced-color behavior.
- Touch targets and mobile software keyboard overlap.
- Reduced motion.

## 10. Definition of done for every slice

- [ ] The slice implements a complete user-visible behavior, not parallel old and new paths without an explicit migration boundary.
- [ ] Every supported language's catalogue has parity.
- [ ] Light and dark themes cover every state.
- [ ] Keyboard order, Escape, focus restoration, live announcements, and touch targets work.
- [ ] Loading, empty, updating, partial, error, offline, and success states affected by the slice are designed.
- [ ] Canonical URLs support Back, forward, reload, bookmarking, and sharing; obsolete route forms are no longer generated.
- [ ] No setting changes scope, persistence, or sync behavior accidentally.
- [ ] Existing stored data still materializes to the same IDs and field values; no UI path clears or rewrites them implicitly.
- [ ] Existing calculations and export content remain unchanged unless separately specified.
- [ ] Relevant unit, component, and end-to-end tests pass.
- [ ] `<check-command>` passes without warnings.
- [ ] `<e2e-command>` passes for a release-bound slice.
- [ ] `<bundle-size-command>` passes.
- [ ] Relevant `MAP.md` files and this plan are updated when responsibilities change.

## 11. Final product acceptance

Before removing the migration label, run these tasks with a newer user and an experienced user:

1. Open existing locally stored data and existing server-synchronized data, confirm every field, edit one value, reload, and confirm both remain intact.
2. Add an item, understand what is missing, and reach its detail view.
3. Switch between items while remaining in the same valid feature.
4. Change the variant and move among all result views without losing context.
5. Select an item in a visualization and find its meaning immediately.
6. Apply a temporary override, then separately save a default.
7. Enter a target date, change a method setting, and filter a list.
8. Configure and cancel a staged settings dialog, then apply several settings in one pass.
9. Expand a disclosure without guessing that a triangle is interactive.
10. Export the current view, build a document, and create a full-data backup from their correct scopes.
11. Recover from incomplete data, a zero-result filter, an offline network action, and a calculation failure.

The migration succeeds when users complete these tasks without being taught the menu hierarchy, without guessing a setting's scope, and without encountering two visual or behavioral versions of the same control.
